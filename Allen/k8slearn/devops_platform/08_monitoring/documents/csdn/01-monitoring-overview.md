# Kubernetes 监控体系全景指南：从入门到精通

> 🎯 **一句话精华**：监控系统就像汽车的仪表盘，让你随时掌握系统的"健康状况"——没有它，你就是在闭着眼睛开车！

## 一、秒懂定位（30秒版）

**这个知识解决什么问题**：
```
你的服务器凌晨3点宕机了，你却在睡觉...
你的应用内存泄漏了，你却浑然不知...
你的磁盘快满了，你却还在往里写日志...

监控系统就是你的"24小时保安"，帮你盯着一切，出问题立刻叫醒你！
```

**适合谁学**：DevOps 工程师、SRE、运维人员、想了解云原生监控的开发者
**不适合谁**：只想看看热闹的吃瓜群众（当然，看看也无妨 😄）

## 二、开场故事：一个没有监控的悲惨夜晚

> 话说某年某月某日凌晨 3 点，小王正在做着升职加薪的美梦...
> 
> 突然，手机响了——不是闹钟，是老板的夺命连环 call！
> 
> "小王！网站挂了！用户投诉电话打爆了！"
> 
> 小王一脸懵逼地爬起来，登录服务器一看：磁盘满了。
> 
> 日志文件把 100G 的磁盘写满了，而这个问题其实 3 天前就开始了...
> 
> 如果当时有监控系统，小王早就收到告警了，哪至于被老板半夜叫醒？

**这就是监控的价值：让问题在"小火苗"阶段就被发现，而不是等到"火烧连营"才知道！**

## 五、核心组件详解

### 5.1 Prometheus - 监控界的"数据库"

**角色**：数据采集、存储、查询的核心引擎

**生活化比喻**：
```
Prometheus 就像医院的检验科：
- 定期采集样本（抓取指标）→ 护士每天来抽血
- 保存检验结果（存储数据）→ 检验报告存档
- 提供查询服务（PromQL）  → 医生查看历史记录
- 发现异常指标（告警规则）→ 指标异常自动通知
```

**主要功能**：
- 🔄 定期抓取 Exporter 暴露的指标
- 💾 存储时序数据（默认保留 7-15 天）
- 🔍 提供 PromQL 查询语言
- ⚠️ 评估告警规则

### 5.2 Grafana - 数据的"画家"

**角色**：数据可视化和 Dashboard 管理

**生活化比喻**：
```
Grafana 就像体检报告的图表设计师：
- 把枯燥的数字变成直观的图表
- 一眼就能看出健康状况
- 可以对比历史数据
- 还能设置"红黄绿"预警颜色
```

**主要功能**：
- 📊 连接多种数据源（Prometheus、MySQL 等）
- 🎨 创建丰富的图表和 Dashboard
- 🔧 支持变量和模板
- 🔔 配置告警通知

### 5.3 AlertManager - 告警的"智能管家"

**角色**：告警通知的管理和分发

**生活化比喻**：
```
AlertManager 就像医院的急诊分诊台：
- 接收各种报警信息 → 病人来了
- 判断紧急程度（分组）→ 这是感冒还是心脏病？
- 避免重复通知（去重）→ 同一个病人不用挂两次号
- 通知对应的医生（路由）→ 心脏病找心内科，骨折找骨科
```

**主要功能**：
- 📥 接收 Prometheus 发送的告警
- 📦 告警分组、去重、静默
- 🚦 路由到不同的接收器
- 📱 发送通知（邮件、Webhook、钉钉等）

### 5.4 Exporter - 数据的"翻译官"

**角色**：采集特定系统的指标

**生活化比喻**：
```
Exporter 就像各种体检设备：
- 血压计测量血压 → Node Exporter 测量节点
- 心电图测量心脏 → cAdvisor 测量容器
- 血液检测仪分析血液 → KSM 分析 K8s 资源
```

**常见 Exporter**：

| Exporter | 采集对象 | 主要指标 |
|----------|---------|---------|
| Node Exporter | 节点 | CPU、内存、磁盘、网络 |
| Kube-State-Metrics | K8s 资源 | Pod、Deployment、Service 状态 |
| cAdvisor | 容器 | 容器资源使用 |

### 6.2 两条数据流路径

1. **告警路径**：Prometheus → 规则评估 → AlertManager → 通知
2. **可视化路径**：Prometheus → Grafana → 用户查看 Dashboard

### 6.3 关键时间点

| 阶段 | 默认间隔 | 说明 |
|------|---------|------|
| 指标抓取 | 30s | Prometheus 抓取 Exporter |
| 规则评估 | 30s | 评估告警规则 |
| 告警触发 | for 时间 | 持续满足条件才触发 |
| 告警分组 | 30s | 等待收集同组告警 |
| 重复通知 | 4h | 同一告警重复发送间隔 |

## 八、监控范围总结

### 8.1 基础设施监控

| 监控对象 | 主要指标 | 数据来源 |
|---------|---------|---------|
| 节点 | CPU、内存、磁盘、网络 | Node Exporter |
| Pod | 资源使用、状态、重启 | cAdvisor + KSM |
| 容器 | CPU、内存、文件系统 | cAdvisor |

### 8.2 应用监控

| 监控对象 | 主要指标 | 数据来源 |
|---------|---------|---------|
| CI/CD | Pipeline 执行情况 | Tekton/Jenkins Metrics |
| GitOps | 应用同步状态 | ArgoCD/Flux Metrics |
| 自定义应用 | 业务指标 | 应用内置 Exporter |

## 十一、常见问题

### Q1: 监控系统本身挂了怎么办？

好问题！这就是"谁来监控监控系统"的哲学问题 😄

解决方案：
1. 监控系统高可用部署
2. 使用外部监控服务作为备份
3. 设置心跳检测

### Q2: 监控数据会不会占用很多存储？

会的，但可以控制：
1. 设置合理的数据保留时间（7-15天）
2. 调整抓取间隔（不需要太频繁）
3. 使用远程存储（如 Thanos）做长期存储

### Q3: 告警太多怎么办？

这是"告警疲劳"问题：
1. 设置合理的阈值
2. 使用告警分组和去重
3. 定期 review 告警规则
4. 只告警需要人工介入的问题
